# Gokul backend (step 1: POS core, step 2: Office, step 3: identity, barrels, backups)

Rust core in `crates/core` (`gokul-core`, no Tauri). Both apps (`apps/pos/src-tauri`, `apps/office/src-tauri`) are thin shells over it and share one database file: `%APPDATA%\GokulRetail\gokul.db`.
Rules live in `.claude/skills/gokul-backend/SKILL.md`. The screens call only the `Api` interface in `packages/data`.

## How a screen call travels
`api.saveBill(draft)` -> `packages/data/src/tauri/tauriApi.ts` -> Tauri command `gokul_call(method, args)` -> `gokul_core::dispatch` -> SQLite.
One command carries every method (names and argument order are identical to the TypeScript `Api`), so the shells stay tiny and every method is testable without Tauri. Errors come back as plain-English strings.
The shells call `gokul_core::dispatch_session(db, session, method, args)`; the session-less `dispatch` is for tests and internal jobs only.

## Identity and permissions (step 3, fraud control)
The signed-in user lives in Rust, never in JavaScript. Each app process owns one `Session` (`Session::pos()` / `Session::office()`; Office refuses cashier accounts).
- `verifyPin` signs in (and signs out first, so a failed attempt leaves nobody signed in). `logout` signs out; the POS lock screen and every sign-out call it. Only `getSettings`, `listUsers`, `verifyPin` and `logout` work signed out; everything else answers "Please sign in first." The screens catch that (and "no longer active") and go back to the login page.
- Every other call runs as the session user (`crates/core/src/authz.rs`): the user is reloaded from the DB with the role matrix as stored right now, the names and user ids the screen sent (`cashier`, `by`, `userId`) are overwritten, and a thread-local actor makes `audit()`, `post_movement()`, `drawer_entry()` and the other "by" columns write the real name. Nothing audits as "Office" any more once a user is signed in (the demo seed and tests, which have no session, still do).
- The role matrix is enforced in Rust: items, categories and brands need `canManageItems` (a changed price also `canEditPrices`); purchases, suppliers, production and norms `canManageStock`; collections `canCollectCredit`; users, roles and PIN resets `canManageUsers`; settings, backup now and restore `canChangeSettings`; reports `canSeeReports`.
- Overrides carry a `managerPin` in the call, verified with argon2 against owners and managers whose role holds the permission: `cancelBill` (`cancel_bill`), `createReturn` (`return`), `createAdjustment` and `postStockTake` (`stock_adjust`, so a manager re-confirms stock changes), `addCashEntry` with kind out (`open_drawer`), and `saveBill` for a discount above the role limit (the approver's own limit must reach it, so a manager cannot approve 20% but the owner can), a line price different from the item master (`price_override` / `canEditPrices`) and credit above the customer's limit (`credit_over_limit`). The error is always "A manager PIN is needed to ..." so the screens know to open the PIN box (`ManagerPinDialog` in `@gokul/ui`) and send the same call again with the PIN. A used approval writes an `override` audit row naming the approver. Day close (Z) still needs a manager PIN. Removing a scanned line calls `logVoidedLine` (see Round 2B below): always logged, and a manager PIN only when Settings, Security asks for it.
- **Lockout**: 5 wrong PINs lock that user for 60 s (`security.lockoutAttempts` and `security.lockoutSeconds` in `settings`; counters in `users.failed_pins` and `locked_until`, so POS and Office share them). A locked user is refused even with the right PIN ("... locked for 42 s."), `listUsers` carries `lockedForSecs` so the login screens show a countdown at once, and `login_failed` and `lockout` rows are audited. Wrong approval PINs (cancel, refund, discount, `verifyManagerPin`, Z) count against the signed-in user the same way; the fifth locks them and signs them out, so a cashier cannot guess a manager PIN.

## Database
SQLite (bundled), WAL, `synchronous=FULL`, `foreign_keys=ON`, busy timeout 5 s. Migrations are numbered files in `crates/core/migrations`, applied at startup in a transaction (`PRAGMA user_version`). Never edit a shipped migration; add the next one.

Money is `i64` paise, quantity is `i64` milli-units. Times are UTC ISO text; `day` columns hold the local date.

| Area | Tables |
|---|---|
| Setup | `settings` (key/value), `sequences` (gapless counters per series and financial year) |
| People | `users` (PIN stored as argon2id hash only), `customers` |
| Catalogue | `categories`, `items`, `barcodes` (many per item, one primary) |
| Day | `shifts` (open/close, opening cash, denominations, Z report), `cash_movements` |
| Sales | `bills`, `bill_lines`, `bill_payments` (cash/upi/card/credit/credit_note), `bill_slabs` (GST per rate), `bill_cancellations`, `bill_reprints`, `held_bills` |
| Returns | `credit_notes`, `credit_note_lines` (returns, exchanges and refunds; own number series) |
| Stock | `stock_movements` (the ledger; `items.stock` is its cached sum, checked by tests) |
| Trail | `audit_log` |
| Catalogue (v2) | `brands`, `stock_adjustments` (reason + ledger row); `items` gained `kind` (`item`, `seed`, `material`), `parent_id` (packed item -> the loose item it is filled from) and `scale_code`. Raw seeds and packing material are items of kind `seed`/`material` in hidden categories `_seed`/`_material`; they never show at the counter, in item lists or in search |
| Purchasing (v2) | `suppliers`, `purchases` (+ input GST columns, `paid` grows as payments are applied oldest first), `purchase_lines`, `supplier_payments` |
| Production (v2) | `barrels` (8 empty ones from the migration), `pressing_batches` (keeps the norm in force when pressed), `pack_runs`, `pack_run_lines`; norms are rows in `settings` (`norm.groundnut.kgPerL`, `.density`, `.settleDays`, same for sesame and copra, and `norm.packWastagePct`) |
| People and money (v2) | `customer_payments` (receipts `RC-26-000001`), `roles` (permission matrix as JSON), customer `type/business/gstin/email/address`, user `pin_changed_at`, `backup_log` |

Nothing is deleted: database triggers refuse DELETE on bills, lines, payments, credit notes, the stock ledger and the audit log, and refuse UPDATE on lines, payments, the ledger and the audit log. A cancel only flips `bills.status` and adds rows.

Numbers: `GK-26-000123` (bill prefix from settings, financial-year digits, six-digit sequence, 12 characters). Credit notes `CN-26-000001`, Z reports `Z-26-000001`. Each series restarts on 1 April and has no gaps: the counter is bumped inside the same transaction as the document, so a failed save gives the number back.

Saving a bill (`bills::write_bill`) is ONE transaction: bill, lines, GST slabs, payments, stock movements, item stock, customer balance and audit row, committed before the call returns. The server recomputes line amounts and totals with the money engine and refuses payments that do not equal the bill total.

### How the Office operations behave
- **Purchase (GRN)** is ONE transaction: `purchases` row (gapless `PU-26-000001`), lines, input GST (CGST+SGST, or IGST when the supplier GSTIN state differs from the shop's), one `purchase` ledger row per line (items, seeds and packing material alike), `items.stock`, optional cost update (rate after discount, ex-GST), cash paid at entry out of the open drawer, audit. Totals come from `compute_grn` (a port of `computeGrn`; trade discount kept as basis points; total rounded to the rupee).
- **Supplier payment** clears the oldest unpaid purchase first and cannot exceed what is due; cash payments go out of the open drawer. The ledger is purchases (debit), paid-at-entry and payments (credit) with a running balance.
- **Pressing batch**: seed (and palm jaggery) out and oil cake in as `production` ledger rows. Oil becomes stock only when the batch is moved to a barrel (`production` row on the loose oil item, `barrels.level_ml` up). **Packing run**: loose oil out (`packing` row, includes wastage), packed items in, barrel level down; the barrel frees itself at zero. Pack sizes are the items whose `parent_id` is the barrel's loose oil item. Barrel level always equals oil moved in minus oil packed (tested).
- **Customer collection** reduces `customers.outstanding`, writes a numbered receipt and (cash only) a drawer entry. Payments clear the oldest credit bill first: the open invoices are the newest credit bills that add up to the outstanding balance, and anything older than the first bill shows as an "Opening balance" line. Ageing, receivables and the statement all use that rule and the statement always ends at the outstanding shown on the customer.
- **Permissions**: `roles` holds the matrix and the "needs manager PIN" list. `cancelBill` asks the roles table: a role that holds `canCancelBill` and does not list `cancel_bill` under needs-PIN may cancel on its own; a cashier (or an unknown name) must give a manager or owner PIN. The owner role is locked to everything. The last active owner cannot be demoted or deactivated. User PINs are argon2id hashes only; `resetUserPin` returns a new random 4 digit PIN once.
- **Settings**: the five tabs are stored as JSON in `settings` (`bundle.*`); saving also writes the keys the counter and receipts read (`shopName address gstin phone receiptFooter printer roundToRupee`).
- **Loose oil and barrels** (`barrels.rs`, migration 003): a loose item is named `<Oil> (Loose)` and is poured from the barrels holding that oil. Saving a bill takes the quantity out of those barrels in the same transaction (`barrel_movements`, an undeletable ledger); a return or a cancel puts back only what that bill drew, the barrel drawn last first, each up to its capacity. Which barrel: FIFO, the barrel filled first (`filled_on`) is emptied first, then the next one. That is how the shop works (one barrel on the tap until it runs dry) and the oldest oil must go first because wood-pressed oil keeps only months. An emptied barrel frees itself like after packing. If the barrels hold less than the bill sells (opening stock that was never put in a barrel) the bill still saves in full and only what the barrels hold is drawn: a sale is never refused over barrel bookkeeping. Barrel level = oil moved in - oil packed - oil sold + oil returned (tested).
- **Backup**: `backupNow` writes a consistent copy with `VACUUM INTO` to the backup folder (default `%APPDATA%\GokulRetail\Backups`) and prunes beyond "keep". `restoreBackup` checks the copy (`integrity_check`) and stages it as `gokul.db.restore`; the next start of either app swaps it in (the old file is kept as `gokul.db.before-restore-<time>`). If the other app still has the database open the swap waits.
- **Automatic backup** (`backup.rs`): both apps start a scheduler thread with its own connection (`VACUUM INTO` reads a snapshot while billing keeps writing). It checks 8 s after start (so an overdue backup is caught on start) and then every 30 s against the stored schedule (`daily`, `twice` a day, `hourly`, `off` = manual only): a backup is due when the newest good one is older than the latest scheduled time. A Z close also starts a background backup (`day-close`). The newest `keep` copies stay; a failed try (missing folder, full disk) is logged (`backup_log.error`) and retried 30 minutes later. `backupStatus` (last good time, age, `stale` when over 24 hours or never, last error) drives the Office status bar, which turns amber with a warning. Rows are audited as "System (auto backup)". Restore is tested end to end: stage, restart, data is as at backup time, the replaced file is kept.
- **Production norms** are edited in Office, Production, Norms tab (`saveSeedNorms`; `listSeedProfiles` also returns `packWastagePct`).
- **Database cannot open**: both apps show a native Windows error box with the reason and the file path, then exit (`gokul_core::native::show_error`), instead of starting as a silent empty window.

## Reports
Plain SQL over the real tables, cancelled bills excluded everywhere. GSTR-1 and 3B read the stored per-bill GST slabs, so their totals equal the bills (tested): taxable = `SUM(bills.taxable)`, tax = `SUM(bills.gst)`, value = `SUM(bills.before_round)`. B2B means the customer has a GSTIN. Credit notes (sales returns) appear in table 9B and reduce the output tax in 3B. ITC in 3B is the real GST on purchases dated in the period. HSN, item, category and margin reports are line based (the taxable part of each GST-inclusive line, rounded half-up per line), so they can differ from the bill slabs by a few paise per line.

Speed on the 100k-bill database (release build): every report over 30 days is under 60 ms and over 90 days under 110 ms; the whole 440-day history (all 100k bills, 300k lines) takes about 0.6 s for the line-level reports (item-wise, HSN, margin), 0.36 s for GSTR-1, 0.16 s for GSTR-3B and under 0.1 s for the rest. Bill-wise lists the newest 5,000 bills with totals over all of them; the Office Bills list returns the newest 3,000 (about 90 ms). Indexes added: `bills(day,status)`, `bill_payments(mode,bill_id)`, `stock_movements(at)`, `credit_notes(day)`; the report SQL forces the bills-first join order and walks the primary key for "newest N" queries.

## Round 2B: expenses, voided lines, mill daily sheet (migration 004)

### Expenses
- Tables `expense_categories` (10 seeded: tea, transport, salary advance, wages, electricity, rent, repairs, packing material, supplier cash, other; editable, never deleted, a category left out of the list is switched off) and `expenses` (gapless `EX-26-000001`, category id and name at the time, paid from `cash`/`upi`/`bank`, amount, paid to, note, user, approver, `shift_id`, status `active`/`void`, void reason, edit count). Database triggers refuse DELETE.
- Calls: `listExpenseCategories saveExpenseCategories listExpenses addExpense editExpense voidExpense`. `listExpenses` returns rows plus totals (total, count, voided count, by mode, by category).
- Authz: any signed-in user may add. Over `expense.limit` (settings, default Rs 1,000, Settings, Expenses tab) a role that cannot open the drawer on its own needs a manager PIN (`expense_over_limit`; the approver is stored on the row and audited). Edit and void need a reason always and a manager PIN for a cashier (`edit_expense`, `void_expense`). A cashier only ever lists today and cannot back-date (`day` is Office only, and cash can only be for today). Saving categories needs `canManageStock`.
- Cash drawer: a `cash` expense needs an open day, carries its `shift_id`, and `shift::summarise` subtracts the active ones (`expensesCash`, `expensesCount` on X and Z; expected cash = opening + cash sales + cash in - cash out - refunds - cash expenses). Voiding one gives the cash back. Once its shift is closed, the amount cannot change or be voided (the Z report is final): add a correcting entry dated today. UPI and bank expenses never touch the drawer. The old "cash out" entry (`addCashEntry`) still exists; POS keeps only "cash added to drawer" (kind `in`) next to expenses.
- Reports: new `expenses` report (by category, by user, filters by mode); `daily-profit` now shows gross, expenses and net profit (all active expenses by day); the cash book's Expenses column adds drawer expenses.

### Customers and the POS
`customers.notes` (migration 004) is on `CustomerInput` and the customer rows. A cashier can call everything the POS Customers and Sales screens use; `listBillsOn` is forced to today for cashiers (managers and owners get any date and "all days"); `cancelBill` keeps its manager PIN.

### Machine type and punnaku
`pressing_batches.machine` is `W` (wood-pressed) or `R` (rotary), default W for old batches; `PressingDraft.machine` is optional. Cake goes to a separate stock item per machine: Kadalai W / Ellu W / Coco use the existing "... Oil Cake (Loose)" items, Kadalai R / Ellu R are "Groundnut Oil Cake R (Loose)" and "Gingelly Oil Cake R (Loose)" (created the first time they are needed; Coco has no split). Vellam is the palm jaggery item, Malli is "Malli (Coriander)" (created on demand).

### Mill daily sheet (`mill.rs`)
- Tables `mill_sheets` (one per day, `draft` or `closed`, counted stock, frozen snapshot), `mill_op_rows`, `mill_cust_jobs`, `mill_punnaku_rows`. Calls: `getMillSheet(day) saveMillSheet(input) closeMillSheet({day, managerPin}) listMillSheets(limit)`. Needs `canManageStock`; closing needs a manager PIN like a stock adjustment (an owner needs none).
- A draft only stores the rows. Nothing touches stock until close, so the supervisor can edit freely. The screen shows computed closing live: opening (the stock ledger up to the start of the day, which equals the previous sheet's counted closing once that sheet is closed) + pressed + purchased + kept + sold + packed + adjusted. Oil lines open from the previous sheet's closing (or the barrels plus oil still settling) and are not posted.
- Close is ONE transaction: operator rows become pressing batches (stock check as for a normal batch; a failure rolls everything back); customer aravai posts nothing to shop stock except cake the shop keeps (ledger row `mill_job`); the charge is one credit bill per customer (item "Aravai Job Work (per kg)", `items.service = 1` so it has no stock and never shows in stock or low-stock lists, HSN/SAC and GST rate from the settings, price per kg from the rate for that job, GST inside the price, on the customer's account so it shows in Collections; the same item can be sold at the counter); punnaku purchased goes in as purchase rows; each counted difference is posted as a `correction` stock adjustment noted "Mill sheet <date>". The printed variance is the difference before those adjustments. Oil differences are only recorded on the sheet (a barrel stock take settles them).
- A closed sheet is read-only (save and close refuse; the frozen copy is returned) and cannot be deleted.
- Demo data: three closed sheets (3, 2 and 1 days ago) with W and R rows, customer jobs (cake taken and kept), punnaku bought and small counted differences, plus 10 past expenses.

## Real stock import (owner's stock as at 17-Oct-2026)
Code: `crates/import` (`gokul-import`). Source: `data/import/clean/items_stock.csv`, all 925 rows loaded as given (no merging, no skipping, negative and zero stock included, zero-stock items active).

What it does, in one transaction: seeds only the shop settings and the five login users (`seed_demo::seed_login_and_settings`; roles, barrels, norms and expense categories come from the migrations), creates categories, brands and suppliers, then one item per row with one `opening` stock movement each, written through `db::post_movement`. Demo items, customers, bills, purchases, production and mill sheets are not loaded.

Run (Gokul POS and Office closed, from the repo root):
```
cargo run -p gokul-import --release                  # the normal database and the CSV above
cargo run -p gokul-import --release -- --db <file>   # any other database, e.g. a scratch copy to rehearse
```
It refuses to run when the database already has items. To load again, close the apps, move `gokul.db` (with `-wal` and `-shm`) out of `%APPDATA%\GokulRetail` and run again.

Checks, before anything is committed (any failure rolls back everything): 925 items; quantity 10,217.539 (shown 10,217.54); value at cost Rs 27,96,290.80; stock ledger equals items' stock per item; 611 positive, 270 zero, 44 negative; the file's stock value equals quantity x cost on every row.

Backup taken before the real load: `%APPDATA%\GokulRetail\backup-before-real-import-20261107-002022\` (the demo `gokul.db` with its `-wal` and `-shm`). The demo file was renamed in place to `gokul.db.demo-replaced-20261107-002022`.

## Printing (round 3, bill layout replaced in round 4)
Code: `crates/print` (`gokul-print`: layout, ESC/POS bytes, Windows spooler, Windows-driver GDI, logo raster; no database) and `crates/core/src/printing.rs` (builds each document from the saved records and sends it). Both apps reach it through `gokul_call`: `printDocument(kind, id, opts)`, `printerStatus()`, `testPrint(kind, printer, opts)`.

**What prints** (same content as `ReceiptPreview`, English): tax invoice / bill of supply (shop header from Settings, logo, GSTIN, FSSAI, number, date, time, cashier, customer and customer GSTIN for B2B, HSN, lines with qty x rate and discounts, round off, total, GST slab table CGST/SGST, payments and change, points earned and balance, "You saved" against MRP when Bill format says so, footer, UPI or bill-number QR, Code 128 of the number, DUPLICATE COPY on reprints, CANCELLED on cancelled bills), credit note, X report, Z report, expense voucher, customer payment receipt. The mill aravai bill is a normal bill (`kind: bill`). Tamil and the rupee sign print as pictures (see round 4 below); any other non-ASCII text in a plain line prints as `?`.

**When it prints.** `saveBill` commits first; the POS then calls `printDocument('bill', id, { auto: true, change })` without waiting, so the next bill never waits for paper. The database lock is held only while the receipt is built; the spooler call happens after it is released. A printing problem is an answer `{ ok: false, message }`, never an error: the bill stays saved and the POS shows "Bill saved. Printing failed: <reason>. Press Ctrl+P to reprint." Ctrl+P on Billing reprints the last bill; Ctrl+P / Enter on Sales reprints the selected one (DUPLICATE COPY, logged by `recordReprint`). Auto-print off: nothing is printed but a cash sale still opens the drawer. The drawer pulse is sent at the start of the bill job when the bill has a cash payment and "Open cash drawer on cash sale" is on; reprints never open it.

**Settings.** Office, Settings, Printers: printer (the real list from Windows with ready / offline / paper-out state, port and driver), how to print (Thermal ESC/POS or Windows driver), auto-print, logo, drawer, cutter, Print test bill (a real job). Bill format: paper 80 mm (48 columns) or 58 mm (32 columns), copies, QR (UPI id or bill number), savings, HSN, GST table, header, footer. Stored in `bundle.printers` (new keys `mode`, `printLogo`) and `bundle.billFormat` (new key `upiId`); `detected` is read-only and always live.

**Status.** `printerStatus()` answers `{ configured, ready, state, name, mode, message }`. The POS top bar dot and the login screen use it (refreshed every 20 s and on window focus); it works signed out.

**Modes.** ESC/POS sends RAW bytes through the spooler (`OpenPrinter`, `StartDocPrinter` with datatype RAW, `WritePrinter`). Windows driver mode prints the same lines with GDI (Consolas, bold and double size, logo bitmap, QR and barcode drawn as dots) for laser, inkjet or PDF printers. A printer name `FILE:C:\path\job.bin` writes the raw job to a file instead (support calls and tests).

**Setting up a printer.** 1) Install the printer's Windows driver (TVS RP3160, Epson TM-T82, Posiflex, Retsol and other ESC/POS printers: the maker's driver, or the Epson TM-T82 driver). 2) Plug in, switch on, check it shows in Windows Printers. 3) Office, Settings, Printers: choose it, keep "Thermal (ESC/POS)", press Print test bill. 4) Bill format: choose 80 mm or 58 mm. 5) Cash drawer: RJ11 cable from the drawer into the printer's drawer port. Supported: any ESC/POS thermal printer (raster logo `GS v 0`, native QR `GS ( k`, Code 128 `GS k 73`, partial cut `GS V 1`, drawer `ESC p 0`).

**Troubleshooting.** "no printer is chosen": pick one in Settings. "not installed on this computer": the saved name no longer exists in Windows Printers; choose it again. "offline": power, cable, or Windows has "Use Printer Offline" ticked. "out of paper" / "door open" / "jammed": fix the printer; the bill was saved, press Ctrl+P. Garbage characters: the printer is not ESC/POS, choose "Windows driver". Logo too dark: untick "Print the shop logo". Cut does not happen: untick "Cut paper after each bill". Drawer does not open: check the cable is in the printer's drawer port.

**Tests.** `cargo test -p gokul-print` (golden bytes at 48 columns, golden text at 32, wrapping of long and Tamil names, QR and barcode round trip, logo is 1-bit and cached, spooler reports missing printers) and `cargo test -p gokul-core --test printing` (printed bill equals the saved bill at 80 and 58 mm, amounts right-aligned, no line wider than the paper, DUPLICATE and drawer rules, a printing failure never rolls back a bill, auto-print off, X report drawer lines add up to expected cash). Samples: `docs/design/shots/print-*.txt` (and raw `.bin` jobs).

## Shop hardware setup (round 4)
The shop's own hardware: **TVS RP3200 Plus** bill printer (80 mm, USB, ESC/POS, cash drawer port), **Retsol** USB barcode scanner (keyboard wedge), **TSC TE244** sticker printer (4 inch, 203 dpi, USB, TSPL). Do these steps once on the shop PC.

**1. Drivers.** Install the maker's Windows driver for each printer from the TVS Electronics and TSC websites (search "TVS RP3200 Plus driver" and "TSC TE244 driver"), then plug the printer in and switch it on. Open Windows, Settings, Bluetooth and devices, Printers and scanners: both must be listed, with no "Offline". Leave the printer names as the driver gives them (for example "TVS RP3200 Plus" and "TSC TE244"): Gokul looks for **RP3200** or **TVS** in the name for the bill printer and **TE244** or **TSC** for the sticker printer, and picks them by itself the first time. The scanner needs no driver.

**2. Choose the printers.** Gokul Office, Settings, Printers. The bill printer card shows the TVS printer already chosen with Thermal (ESC/POS), 80 mm (48 columns), cutter on and cash drawer on. Press **Print test bill**: a bill with the logo, Tamil lines and a barcode must come out and the paper must cut. In the sticker card pick the TSC printer. Press **Save changes** at the bottom.

**3. Bill printer trouble.** Rubbish characters: choose "Windows driver". Printer stops or prints strange symbols when a logo or QR comes: turn on **Compatibility mode** (no logo, no QR, no Tamil pictures, only text, barcode and cut). Drawer does not open: the cable goes in the printer's drawer socket (RJ11), and "Open cash drawer on cash sale" must be on. Cut does not happen: untick "Cut paper after each bill". The commands used are the common ESC/POS ones the RP3200 Plus supports (reset, code page 437, bold and double size, `GS v 0` raster for the logo and Tamil lines, `GS ( k` QR, `GS k 73` Code 128, `GS V 1` partial cut, `ESC p 0` drawer); not yet confirmed on the real printer, so the first test print at the shop is the check.

**4. Scanner check.** Settings, Printers, Barcode scanner card: click the box, scan any label, press Enter. It says how many milliseconds passed between characters and whether it looks like the scanner. If a real scan is called typing, raise "Fastest key gap that counts as a scan" (default 30 ms) above the slowest gap shown. A Retsol **laser** scanner reads 1D barcodes only (Code 128, EAN-13). The **QR code** stickers need a **2D (imager) scanner**: with a laser scanner use the Barcode option on the Labels screen instead of QR.

**5. Sticker calibration.** Load the 38 x 25 mm roll (gap sensor type "gap"; run the printer's own auto-detect once by holding the feed button). Settings, Printers, sticker card: size "Gokul small 38 x 25 mm", press **Print test label**. The frame must sit exactly on the sticker edge and nothing may be cut off. If it is shifted, change "Shift right" and "Shift down" (8 dots = 1 mm) and print again. Upside down: tick "Labels come out upside down". Too light or too dark: change Darkness (8 is normal). Then print real stickers from Barcode labels (tick items on the Items screen and press Print labels, or pick them there).

**Scanning at the counter.** Scan anywhere on the billing screen, even while a quantity box is being edited: the item is added by its exact code or barcode (shop codes like G123 too), scanning the same item again adds one more. A code that is not found gives a short beep and a message. On Returns and Sales a scanned bill barcode finds that bill (with a bill open on Returns, a scanned item ticks one unit). On other screens a scan shows the item's price and stock. The scanner is told from typing by speed only, so nothing a person types is lost.

## Printing, round 4: the bill, Tamil, labels
**Bill layout** (matches the shop's POS Bean bill; `bill_doc` in `crates/core/src/printing.rs`): logo, shop name, Tamil line, address, `GSTIN: ...`, `Mobile.No : ...`; heading by payment mode ("Cash Bill", "BHARATQR Bill", "Card Bill", "Credit Bill", all editable in Bill format) with the small line TAX INVOICE / BILL OF SUPPLY under it (GST rule 46 needs the word); customer block for a named customer (name, Cust ID, contact, address, points balance with two decimals); `BILL NO : 26/00123  DATE`, `Counter  TIME hh:mm:ss`; PRODUCT, MRP, RATE, QTY, AMT; ITEMS and TOTAL QTY; TOTAL; big NET AMOUNT; Tax %, Taxable Val, SGST, CGST, Total Amt; boxed Payment Details with Amount Received and Balance for cash; "For Orders: WhatsApp", the Tamil footer line and the footer line; barcode of the printed bill number. Samples: `docs/design/shots/print-gokul-cash`, `-upi`, `-cash-58mm` (`.txt`, `.png` and the raw `.bin`).

**Tamil and the rupee sign** are drawn with a Windows font (Nirmala UI, else Latha or Vijaya) into a 1-bit picture and sent as raster `GS v 0` (`crates/print/src/tamil.rs`, cached per line). Needs a Tamil font on the shop PC (Windows 10 and 11 have Nirmala UI). Without one the line is left out and the English text prints. Compatibility mode sends no pictures. Optional setting "Print Tamil item names" prints each item's Tamil name as a picture.

**Bill numbers** stay gapless (`GK-26-000123` inside). The printed form is `YY/NNNNN` (`26/00123`, YY = financial year) and a scanned or typed `26/00123` finds the bill on Returns and Sales. Setting Bill format, "Printed bill number" can show the internal one. Numbering starts fresh in this software (no continuation of POS Bean numbers).

**Points** are held in hundredths (migration `006_points_hundredths.sql`, existing balances multiplied by 100, tested on a copy of the real database): one point per Rs 100 of money paid, so Rs 460 earns 4.60, nothing is rounded down. Redeeming is still in whole points.

**Shop details** of the owner's bill (name SRI GOKUL ENTERPRISES, short name GOKUL, Tamil line, address, GSTIN, mobile and WhatsApp, footers) were written through the settings API with `cargo run -p gokul-core --example apply_shop_settings -- <path to gokul.db>` (apps closed). Everything stays editable in Settings, Shop and Bill format.

**Labels** (`crates/print/src/tspl.rs`, `crates/core/src/labels.rs`): TSPL jobs sent RAW through the spooler. Default size **Gokul 3-up (33x25)** (33 x 25 mm, three across, 2 mm gap = 280 dot pitch, 3 mm rows, SIZE 103 mm; the TE244 prints 104 mm). Inside a 2 mm safe margin on all sides (16 dots, content box x 16..248, y 16..184): GOKUL in bold with Pkd / Exp small on the right, the name in capitals centred, then one block centred: the QR of the item barcode or code (63 dots), and to its right the rupee picture and price with the code under it. Nothing below the block. `startMm` (0 to 5, default 0) moves the content in from the left edge. Settings: "Ribbon (thermal transfer)" (`SET RIBBON ON`, on for the TE244) and "Rupee sign" (picture of the rupee from a 1-bit BITMAP, then Rs.; picture only; or Rs. only). The rupee picture is a 12 x 16 dot bitmap because the built-in fonts have no rupee glyph. Presets: **Gokul small** 38 x 25 mm (GOKUL, item name in capitals, QR of the exact item code, the code, `Rs.38.00`, `Pkd:` and `Exp:` blank unless a pack date is typed in the print dialog; a date is never invented), 50 x 25, 38 x 25 two across (79 mm), 33 x 25 three across (103 mm; the TE244 prints 104 mm), 100 x 50, and custom size, gap and columns. Fields: shop, name, MRP, price, Code 128 or EAN-13 barcode (real EAN-13 numbers are drawn as EAN-13), QR, pack date and best before, batch, net quantity, Legal Metrology line. The Labels screen preview is drawn from the same element list as the printer commands (`labelPreview`), so it matches the sticker. Identical stickers in a row are sent as one `PRINT 1,n`. Calls: `labelPreview(itemIds, opts)`, `printLabels(entries, opts)`, `testPrint('label', printer, opts)`, `getHardware()`.

**Scanner code** (`apps/pos/src/scanDetector.ts`, `scanner.tsx`): the detector holds the first character, and if the next arrives within the gap and Enter ends a burst of at least 3 characters it is a scan; otherwise the held text goes back to the field (or is replayed as a key press for hotkeys). Tests: `npm test` (13 detector cases).

**Tests.** `cargo test -p gokul-print` (barcode patterns, TSPL golden output for every preset, Tamil raster), `cargo test -p gokul-core --test labels` (jobs from the database, preview equals printer text, compatibility mode, hardware defaults), `--test printing` (the new bill at 80 and 58 mm, sample bills), `--test loyalty` (two-decimal points, migration v6 and the ignored `real_copy_upgrades_in_place` run against a copy). A few timing tests (demo seed under 2 s, day close backup) can fail when the whole workspace is tested in parallel on a busy PC; run them alone.

## Drawer reconciliation (X, Z, day close)
`ShiftSummary` carries every drawer movement as its own field: `openingCash`, `byMode.cash`, `cashIn` (of which `collectionsCash`), `cashOut` (of which `supplierCash`), `cashRefunds`, `expensesCash`, plus `expensesOther` (UPI or bank, listed but not in the drawer) and `expenseLines` (by category). Expected cash = opening + cash sales + cash in - cash out - cash refunds - cash expenses. The Day close card, the X panel, the X/Z previews and the printed reports show those lines and they add up exactly (test `drawer_breakdown_lines_sum_to_expected_cash`).

## Credit, store credit and loyalty points (round 3)
- **One credit rule.** `customers.credit_limit`: `0` = credit NOT allowed, above 0 = allowed up to that amount, `-1` = no limit (only when the owner ticks "No limit" in a customer form). A sale on credit to a customer with limit 0 needs a manager or owner PIN (audited override); `setCustomerCredit(customerId, limit, managerPin)` allows credit for the customer (audited, manager PIN for a cashier). Customers made at the counter start at 0. The Payment dialog offers "Allow credit for this customer" or a one-time manager override.
- **Store credit.** Credit notes refunded as "credit note" can be spent in parts (`credit_notes.used`, balance = grand - used) with the Payment method "Store credit"; `getCustomerWallet(customerId)` returns points, store credit and open credit notes.
- **Loyalty points** (`crates/core/src/loyalty.rs`, migration `005_loyalty_credit.sql`, additive only). Settings, Loyalty tab: rupees per point (100), value of a point (Rs 1, **confirm with the owner**), fewest points to use (100), most percent of a bill (100). Earn on the net bill after discount minus the part paid with credit notes or points, with two decimals (held in hundredths, see round 4). Redeem as payment mode `points` (stored as a `credit_note` payment with ref `PTS`, because `bill_payments` cannot be altered). A cancel gives back redeemed and takes back earned points; a return takes back earned points in proportion. `points_ledger` is never deleted or edited; `customers.loyalty_points` equals its sum. Office customer detail has a Points tab. Existing `loyalty_points` become the opening ledger row.
- Tests: `cargo test -p gokul-core --test loyalty` (earn rounding and exclusions, redeem rules, cancel and return reversal, ledger immutability, partial store credit, the credit rule with PIN and audit, migration v4 to v5, and an ignored test run against a COPY of the real database with `GOKUL_DB_COPY`).
